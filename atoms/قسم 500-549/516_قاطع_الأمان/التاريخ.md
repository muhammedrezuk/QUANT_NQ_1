## 5.3.0 — 2026-08-27 (found during a full 304-atom audit, not assumed)

- **Blocking fsync-forcing I/O on the kill-switch hot path.** This atom's
  `Journal` (`shared/durable_execution_journal.py`) opens every connection
  with `PRAGMA synchronous=FULL` -- the strongest, slowest durability mode,
  a full disk fsync on every commit. All four call sites
  (`_flush_outbox`, `_persist_financial_state`, `_trip`'s halt, and
  `_on_loss`'s `reduce_consumer_event`) called it as a plain synchronous
  call directly inside `async def` methods, no `asyncio.to_thread` --
  meaning the atom whose entire job is "halt immediately" could stall its
  own event loop, and every other handler sharing it, for however long a
  full fsync takes under contention. Three other atoms (517, 518, 563)
  share this same `Journal` class and the same blocking call shape --
  not fixed here, flagged for their own turns.
- **The naive fix would have been dangerous, so it wasn't shipped as-is.**
  Wrapping the four call sites in bare `asyncio.to_thread` (matching how
  580 and 30+ other atoms already do this) opens a real await point
  inside `_trip`/`_on_loss` that didn't exist before. Traced by hand
  before writing any code: `_on_loss` for account A snapshots book state,
  starts its threaded `reduce_consumer_event` call, and yields; while
  that's in flight, a concurrent `_trip(A)` (a halt request) sets
  `kill=True` in memory and persists; when `_on_loss`'s delayed call
  finally returns, `b.update(state)` -- built from data read before the
  halt -- **overwrites `kill` back to False**, silently un-halting an
  account that had just been correctly halted, while the durable store
  and the already-published halt event both still say `True`. Real,
  reproduced empirically (not just reasoned about) in a disposable
  scratch copy: `test_7_concurrent_loss_and_trip_kill_flag_not_lost`
  fails against a threaded-but-unlocked variant with exactly
  `kill: False` where it must be `True`, and passes against every other
  variant of the same suite untouched (isolating that this one test
  catches exactly this one bug).
- **Fix: a per-account `asyncio.Lock`** (`self._locks`, `self._lock(a)`)
  now serializes the full mutate+persist critical section in `_trip`,
  `_on_loss`, `_on_reset`, and `_on_day` (per account inside its loop) --
  the event loop still isn't blocked by the fsync-heavy write (still
  off-thread), but two safety-mutating operations for the *same* account
  can no longer interleave and clobber each other. Different accounts
  remain fully concurrent -- no cross-account blocking. Handlers that
  don't touch the kill/loss fields (`_on_account`, `_on_terminal`,
  `_on_ledger`, `_on_positions`, `_release`) were left unlocked: none of
  them gained a new await point, so none of them gained a new race.
- **`الشرح.md`'s hand-written "عقد الكود" section was stale**,
  describing events, config keys, and a version (`1.1.2`) that don't
  match this atom since at least `5.0.0`. Corrected while already here
  for the version bump.
- **One Arabic-language comment in `atom.py`**, pre-existing (not
  introduced this round), violated the project's own atom.py-is-Arabic-free
  rule (م3/ملف4) -- caught by the validator, translated in place, zero
  behavior change.
- **A pre-existing test bug found while restructuring the test file for
  diagnosability** (the original was a single one-line `main()`; an
  `AssertionError` gave no way to tell which of many chained assertions
  failed -- had to write a standalone repro script just to isolate it).
  The test asserted that a loss with an *incomplete* cost breakdown
  leaves the book unchanged -- that was true before v5.1.0 above, and
  the v5.1.0 fix deliberately changed it (a number that arrives COUNTS
  even when incomplete; only a missing number is skipped). The test was
  never updated after that change, so it had been silently asserting
  disproven behavior since 2026-08-25. Confirmed pre-existing, not a
  regression from today's edits, by running the identical assertion
  against an unmodified scratch copy of the original `atom.py` first --
  it failed there too. Split into 8 named functions
  (`test_1`..`test_8`), fixed the wrong assertion to match the
  documented, intentional current behavior, kept every other scenario
  the original covered, and added the two new tests above.
- 8/8 tests passing, validator 0 violations.
- **Not touched, and why:** 517/518/563 share the same blocking
  `Journal` call shape (confirmed by grep, not fixed here) -- each needs
  its own trace of which of its handlers can race on shared per-scope
  state before a lock (or the absence of one) is safe to add, the same
  way 516 needed one here. Applying the pattern mechanically without
  that trace is exactly how the naive half-fix above would have shipped
  a new bug instead of closing one.

## ٢٠٢٦-١٠-٠٢ — `5.10.0`: مجموعة أسباب، وإيقافٌ شامل بلا حساب (ختم المالك: صلح كامل nq)

**ما كان:** (١) الدفتر يحمل سببًا واحدًا: `_trip` يعود صامتًا والمفتاح مرفوع، والمخفِّض لا يضيف سببًا إلّا والمفتاح مفتوح، وسببٌ واحد لكلّ نتيجة (اليوميّ يحجب المتتاليات). فما دام `MAX_EXPOSURE` ممسوكًا — وهو يُرفع بعد كلّ دخول تقريبًا — يضيع خرق الخسارة اليوميّة أو الجلسة أو السحب، ثمّ يفكّ 508 قفله آليًّا فيعود التداول فوق حدٍّ مخروق. (٢) طلب الإيقاف بلا `account_id` يُرمى رفضَ هويّة؛ وهو بعينه زرّ «الإيقاف الطارئ الشامل» في اللوحة وتلغرام (حمولة `{}`)، فلم يوقف شيئًا قطّ (صفّ `halt` واحد في سجلّ الأوامر وحالته `EXPIRED`).

**ما صار:** لكلّ دفتر `reasons` (قائمة مرتّبة بالشدّة)، و`kill` و`reason` (الأشدّ) مشتقّان منها، وحدث `emergency.halt` يحمل `reasons` بجانب `reason`، و`risk.account.state` يحمل `kill_switch_reasons` و`system_halt`. الإيقاف يضيف سببه دائمًا ويُعلَن إن فُتح المفتاح الآن أو صار السبب الجديد أشدّ (لا إعلان مكرَّر غير ذلك). الإفراج الموسوم (508/506/اليوم) يسحب سببه وحده، ويبقى المفتاح مرفوعًا ما بقي سبب. زرّ المالك يمسح الكلّ كما كان (ويصفّر المتتاليات والخسارة اليوميّة). والإيقاف بلا حساب أو بـ`scope=SYSTEM` يوقف كلّ دفترٍ معروف ويُعلَن لكلّ حساب، ويبقى علمًا دائمًا (المخزن تحت المستهلك `516:system` واللقطة `global_halt`) يولد تحته كلّ حسابٍ جديد موقوفًا ويُعلَن، حتى زرّ المالك بلا حساب (أو `scope=SYSTEM`)؛ والإفراج الآليّ واليوم الجديد لا يمسّانه. واللقطة القديمة بسببٍ واحد تُحوَّل، والتالفة تبقى موقوفة. **اليوم الجديد:** يسحب `RISK_DAILY_LIMIT` وحده (حكم ٠٩-١٨ كما هو)؛ والمتتاليات وأمر المالك والإيقاف الشامل وكلّ سببٍ آخر تبقى. لم يُمسّ أيّ حدّ.
